## 文案怎么写

按开发者介绍项目的方式写：项目做什么、怎么启动、支持哪些功能、还有什么没做好。用具体功能名作标题，例如“接口管理”“监控和报告”“测试情况”。

少用口号和抽象表达。例如，把“从接口准备到结果复盘，让每一次压测都有据可查”改成“在网页上配置接口、管理测试账号、执行压测和查看报告”。技术术语可以保留，但需要解释它对应什么操作或数据。

不要为了显得亲切编造作者经历、用户反馈或使用规模。英文版也用正常的技术文档写法，不额外添加宣传语。

限制写在相关操作步骤或支持范围里，不要每一段都重复免责声明。测试结果保留日期、范围、失败和跳过数量。没有实际结果的 CI、部署状态、性能数字，不放进徽章或介绍里。

## 文件分工

`README.md` 是中文首页，`README.en.md` 是英文介绍，两份文档的功能说明和限制保持一致。首页保留项目介绍、主要功能、使用流程、快速开始、支持范围、测试结果和文档入口。

安装细节放在 `docs/getting-started.md`，实现结构放在 `docs/architecture.md`，配置细节链接到已有专项文档。不要把同一套安装命令复制到多处后分别修改。

## 修改后检查

检查相对链接、页面锚点和图片替代文本。查看深浅色和窄屏下是否有截断，代码块和折叠内容是否正常。使用 GitHub 支持的 Markdown 和基础 HTML，不依赖自定义页面脚本。

保留上游署名、许可证及已有测试记录。只改文档时，提交说明写实际做过的检查，不把历史测试结果写成这次重新跑过的结果。
