# k6 本地适配

本分支基于 TestHub `272ab153c6381b8eb726847dee3b2d819f2574ca`，候选适配器 `0.9.0`，尚未发布。本轮增加[同场景有界专项执行](../../deployment/bounded-execution.md)，支持固定 VU 范围、每用户尝试上限、最小间隔及独立统计，保留已合并的 HTTP / WebSocket 行为。下文历史验收不代表本候选发布或业务服务的 1000 并发容量。

## 固定版本与能力状态

[固定版本能力矩阵](k6-capability-matrix.md) `2026-09-20.2` 绑定 k6 `2.2.1-0.20260915101307-0ae3c2989e5b`、源码提交 `0ae3c2989e5b7d24e5d18080aa72aa968ad5015f` 与适配器 `0.9.0`。表单和脚本分别记录已验收、待开发、需要可选依赖、该版本无此功能；矩阵列出所有注册执行器、Options、模块方法组、全局 API、指标、CLI、输出和秘密源。

引擎状态接口在 K6 对象追加 `capabilities`，保留既有 `version`（Docker 为 fingerprint）及其他引擎契约。`baseline` 是审查基线；`runtime` 只返回当前 binary version、已匹配的源码 commit、适配器、runner 模式及 Docker 镜像 ID/hash；`verification.differences` 提示版本变化。未知版本不会借用源码 HEAD 或已验收状态。响应不含账号、密码、运行快照、网络名称或本机路径；复用原 15 秒状态缓存，不遍历 Git 或源码。

原生版本行接受固定版本的 `k6 v…` 和 Windows `k6.exe v…`，整行匹配；其他程序名、多行输出或版本变化无法通过能力矩阵版本核对，页面执行入口保持禁用。接口顶层 `websocket` 表示平台实时监控通道，与 K6 `capabilities.items` 中的业务 WebSocket 发压能力不同。

场景编辑页常显能力摘要，详情默认折叠。能力/场景未加载、版本未核对或 runner 不可用时禁用调试与运行；保留保存配置的能力。原生脚本、完整执行器、复杂协议等未接入项明确显示待开发；代理目前在 Docker 下不支持，原生传递路径尚未验收，页面暂不开放。已存在的其他引擎与原模块结构保留。

调试通过 k6 正常异步执行、停止和报告链，固定 1 VU / 1 轮 / 最长 60 秒（平台最大时长更低时从低），不覆盖场景正式压力配置。网页证据为执行 12，提前停止证据为执行 14，详见矩阵。

## 本地运行范围

`backend.pressure_settings` 只启用登录和性能测试依赖模块，使用独立 SQLite 数据库，绑定回环地址。该配置用于单机验证；正式内网部署需要单独验收数据库、并发调度、权限与部署方式。

目录由 `PRESSURE_PLATFORM_ROOT` 指定。`runtime/private` 保存账号数据、数据库、凭据与运行快照；不映射为静态目录。`runtime/media` 保存平台附件与报告，需经认证接口访问。

## Runner 配置

以下变量由管理服务及其执行 worker 继承；更改后应重新创建任务。

| 变量 | 用途 |
|---|---|
| `K6_RUNNER` | `NATIVE`（默认）或 `DOCKER` |
| `K6_BIN` | 原生 k6 程序路径；未设置时从 PATH 查找 |
| `K6_LINUX_BIN` | Docker 使用的 Linux k6 程序；默认总目录下 `runtime/bin/k6-linux` |
| `K6_DOCKER_BIN` | Docker CLI 路径；未设置时从 PATH 查找 |
| `K6_DOCKER_IMAGE` | 已存在的镜像，默认 `alpine:3.22`；不会自动拉取 |
| `K6_DOCKER_NETWORK` | 已存在的本地 Docker 网络，必填 |
| `K6_DOCKER_CPUS` | CPU 配额，默认 `8`，允许大于 0 且不超过 8 |
| `K6_DOCKER_MEMORY` | 内存配额，默认 `2g`，使用 `m/g` 单位且不超过 2 GiB |

Docker 目标地址必须能从容器访问，不会自动改写 `127.0.0.1`。请配置自己的目标服务地址及独立运行环境；部署说明见仓库根 README。

创建任务时冻结环境、步骤、账号数据、执行编号及 k6/适配器版本。Docker fingerprint 还包含镜像 ID、网络名及 ID、CPU/内存配额、Linux 二进制版本及 SHA256；worker 重验，复制到私密运行目录后的二进制也校验哈希。不匹配时拒绝执行。

Docker 每次创建独立容器，以 `io.testhub.k6.owner`、`io.testhub.k6.execution` 标识归属，只读挂载本次私密目录，不挂载 Docker socket。正常结束、停止和异常启动均清理自身容器；Windows worker 被强杀后，容器内看门狗在心跳序列约 5 秒不再变化时终止 k6。Windows 原生 runner 使用 Job Object 清理子进程。Linux 宿主上的原生 worker 崩溃清理尚未验收。

## 已实现范围与限制

- 固定并发，按每用户轮数或持续时间结束；顺序执行启用的业务步骤。
- CSV 每个池单独保存为私密 JSON，通过 `SharedArray` 按行共享；每 VU 每池只读取自己的一行一次，多列和多轮保持同一身份。账号不足或重复在预检拒绝，不循环复用。
- 支持预存 Token、每 VU 一次前置登录、常量和 CSV 变量；登录失败不发送该用户业务请求。失败请求会清理其提取变量，防止复用上一轮资源。
- HTTP 请求体支持 NONE/JSON；支持基础 JSONPath 提取、状态码/JSONPath 相等断言，断言预期值为字面量。固定思考时间单位为毫秒。
- 手工 K6 WebSocket 步骤使用 `k6/websockets`，每次步骤调用建立新连接，首帧 BEARER Token 认证后串行执行有界 JSON 命令，以同一 `id` 和布尔 `ok=true` 回执判定，再执行命令级基础 JSONPath 规则。按配置保活后关闭，同 VU 后续 HTTP 步骤等待关闭；无自动重连、重发、二进制/图片或 SSE。配置、只读模板及验收边界见 [客服 WebSocket 场景](../../deployment/websocket-scenarios.md)。
- 同一实例 k6 任务串行。暂不支持任意脚本上传、到达率、爬坡、多场景、权重、并行请求、文件上传、复杂 JSONPath/正则、自动重定向或分布式调度；Docker runner 暂不支持代理。未支持配置明确阻止。
- 原项目其他模块并未因接入 k6 而全部启用；当前配置不能视为完整内网管理平台。

## 指标与安全

- `http_started/http_total/http_incomplete` 分别表示开始调用 HTTP 客户端、收到完成事件、尚未收到完成事件的数量；`business_*` 排除前置登录。开始调用不证明服务端已接收。
- HTTP-only 场景的业务 RPS 为已完成业务请求数除以引擎运行秒数，包含启动和登录耗时；不是事务 TPS。混合场景每个 WebSocket 会话计为一个业务步骤，全局完成速率不能解释为消息 QPS。`completed_iterations` 是完整执行轮次，可以包含业务失败。每步骤最多计一次失败。
- 适配器 `0.7.5` 的按时长模式以 `exec.scenario.startTime` 为所有 VU 的共同起点，配置时间包含前置和认证。到期后业务、前置、登录、刷新及重试都禁止发起新 HTTP；在途请求保留断言和提取，收尾上限为请求超时加 5 秒，长思考和重试等待也受截止时间约束。固定轮数模式仍使用 `gracefulStop=0s`，保持最长时限硬截止。
- `summary.timed_load` 区分配置时间、收尾上限、k6 场景 UTC 起止、已观测的到期后请求完成时间和引擎总时长。业务 RPS 分母仍为引擎总时长；原生活跃 VU 观测包含启动和收尾，不得拿其跨度证明配置时长内每一瞬间持续业务并发。活跃 VU 不等于在途 HTTP 或每秒请求数。
- 主动停止、SLA 中止、worker 心跳保护和真实请求超时保持原行为；未完成请求、零业务、前置中断及固定轮次不足不能判为正常成功。到期时仅执行部分业务步骤不算完整轮次。
- 实时采样与结束摘要分别收集。网页累计 P95/P99 使用固定桶直方图估算，不平均窗口分位数；原始 `elapsed_ms` 是包含连接等待和客户端处理的墙钟耗时，可独立计算样本分位数。字节数未采集。
- 原始 CSV 保留既有列并追加数值 `error_code`、固定 `error_category`；结束摘要 `request_error_groups` 按错误码、安全分类和状态码聚合，区分业务与前置请求。不保存原始错误文本、请求头、Token 或实际 URL；URL 列仅记录步骤编号。
- 混合场景的 CSV 额外标记 `protocol` 与 `latency_kind`；HTTP-only 列不变。WebSocket 会话耗时包括建连、认证、命令、保活和关闭，命令 RTT 独立统计，SLA 仍作用于步骤整体。`summary.websocket` 与实时样本分列会话、连接、认证、命令、心跳及实际连接观测；未观察到最终关闭时当前连接数为未知。认证帧和业务响应正文完全省略，公开数据只保留冻结的安全标签、规则编号与结果。
- WebSocket 关闭有界等待，超时通过安全失败事件终止所属 runner；固定轮次的 `gracefulStop=0s` 保持不变，额外引擎看门狗防止原生 socket 在 k6 时限后挂起。按时长模式只允许既有在途命令有界收尾；到期后不建新连接、不发新命令或心跳。
- NATIVE CPU 是 k6 进程占用；DOCKER CPU/内存来自整个发压容器，包含轻量看门狗，不是 Windows Docker CLI。CPU 均按单核 100% 口径，多核可超过 100%；无有效样本为未知。已取消将该数值套用整机 CPU 阈值的误警，CPU 高低都不能单独证明发压器容量；`load_generator_capacity_verified` 仍为 `false`。

## 验证

2026-09-15 执行 10，通过平台正常执行入口使用 Docker 同网目标 `api1:3000`：1000 VU，每人 10 轮，两个只读接口 `/api/v1/me`、`/api/v1/me/notifications/unread`，每请求后等待 1000 ms。结果为 20,000 个业务请求全部成功，两个接口服务端计数各增加 10,000；已发起=已完成，未完成为 0，完整轮次 10,000，耗时 27.66 秒。1000 个 VU 的首末请求完成区间存在 19,819 ms 共同重叠；账号预检、冻结数据哈希和逐 VU/接口数量均通过。

这是本地同机、两个只读接口、有等待的短测，证明本次平台链路可以正确执行并对账；不代表 1000 请求同时在途、最大容量、长期稳定性或上线 SLA。证据：[执行 10](../../evidence/concurrency-probe/probe-10.json)。


最终 `test_k6*.py` 共 69 项全部通过、退出码 0，其中包含 4 项真实 Docker 生命周期测试及 Windows worker 强杀测试；测试后无 runner 残留。CPU 误警修正后另做 22 项定向回归通过。69 项完整日志和历史运行记录保留原样，不改写为修正后的结果：[测试日志](../../evidence/final-k6-readiness-tests-20260915.log)。
